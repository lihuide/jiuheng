# 开源参考实现审计

九衡只把开源术数项目当成独立验证源和工程结构参考。开源许可证解决的是“能否依法使用代码”，不解决“术数规则是否可靠”；README 声称“严格古法”也不是古籍证据。

机器可检查的完整清单位于 `data/research/open-source-reference-implementations.json`。它固定以下流程：

1. 固定仓库 commit 与所读文件哈希。
2. 单独核验 LICENSE/NOTICE。
3. 只提取机械步骤、输入输出字段与测试思路。
4. 同输入运行参考项目和九衡独立实现，逐字段记录一致、误差与分歧。
5. 回到古籍影印本验证规则，完成书目、转录、逻辑、实现四类复核。
6. 只有独立古籍证据与九衡测试均通过后，才可另行建立正式 Rule ID。

任何参考项目的断语、吉凶、用神、应期、行动建议、权重、AI 输出或现代评分都不得进入运行时。没有固定 commit 和文件哈希时，连正式黑盒对拍也不允许执行。

## 太乙首轮审计

`kintaiyi` 的公开入口覆盖年、月、日、时、分、命六类，并输出积数、局式、太乙落宫、文昌、始击、主客定算和八门等丰富字段，适合拆成九衡对拍契约。

v0.35.0 已将参考源固定为 commit `626d8a5bd0f707fec2ed613c83d4b6611f56441d`、Git tree `0a4188c6752905b45cf2b5262c8c08dd3badad81`，并记录确定性 `git archive` 与 15 个关键文件的 SHA-256。该提交包含可核对的 MIT `LICENSE` 文件。固定源码只建立了“所读代码是哪一版”的身份链，不等于获准执行，更不等于规则正确。

但当前仓库不是纯古法机械库：README 明示“分计”为现代延伸，源码包含 AI 客户端，`pan` 还可选择现代 Nash 均衡和线性规划分析。源码中的积数与日干支校准、多个历元常数及“古籍 line”注释仍需回到影印本逐项校验。因此 v0.35.0 首轮只登记字段和三组输入，不保存任何可信期望输出。当时的“没有九衡独立太乙实现”已不是现状：截至 v0.75.0，九衡已有年计、显式阴阳遁七十二局、主客大小将、岁计门盘与多类机械位置关系，但现代日期到局序和完整占断仍未完成。

2026-09-27 已完成第一项**静态字面量算数表比较**：核验同一固定提交的 `config.py` 原始字节与 MIT 许可证，只用语法树读取 `find_cal` 中的 `yangcal`、`yingcal` 两张常量表；不导入 Python 模块、不运行第三方函数、不加载 pickle，不引入 AI/联网依赖。九衡独立 Rust 实现对照显式阴阳遁的 144 个局序、288 个主客算值，140 局完全一致，4 局各有一个差异；已逐格登记并增加自动测试。这不是完整时间起局黑盒对拍，也不证明古法正确或现实准确率。详见 [太乙主客算开源对照报告](TAIYI_OPEN_SOURCE_COUNTS_CROSSCHECK.md)。

## 七政四余首轮审计

`kinastro` 确实提供了很有价值的目录：七政位置、四余位置、宿度、十二宫、行限、流时、张果与择日被拆成独立模块；Horosa 的第三方声明也明确其 vendored `kinastro` 为七政页面后端来源。

v0.35.0 已将参考源固定为 commit `bde4fb4044cbc317911ba988dcb6459f7e10ec4a`、Git tree `0bd84950c61e42b5d74357c5aa2bc6e85f76ccad`，并记录确定性 `git archive` 与 9 个关键文件的 SHA-256。固定提交暴露了此前网页检查未发现的许可缺口：README 与 `pyproject.toml` 声明 MIT，README 也链接 `LICENSE`，但该提交实际没有 `LICENSE` 文件。因此九衡把它降为“许可未闭合”，在补齐或获得明确许可前不复制、不分发、不作为依赖。

但它适合作为“发现待验证步骤”的来源，不适合作为标准答案：

- 行星由 Swiss Ephemeris 计算，不符合九衡最终免大型星历的实现约束，只能用于交叉验证。
- 立命岁差常数 `29.185°` 在源码中说明为依据单一 1985 香港案例反推；“今制”宿界又在同一案例上整体平移 `1.5764°`。
- 代码用 Placidus 计算上升点，随后又以 30° 等分映射地支宫，混合口径必须拆开审计。
- 罗睺、计都、月孛、紫气映射只是实现选择，必须从七政四余古籍和历算传统重新核实。
- 行限模块明确称为“简化法”，并按西方黄道守护星分配地支宫，不能直接用于九衡。

因此首批七政工作契约只包括：输入时刻/地点、儒略日、七政黄经黄纬速度、四余候选、宿名与入宿度、边界安全、立命依据、十二宫和星曜落宫。所有期望输出暂为空；先完成行星算法选型、误差预算、宿界历元和四余定义的古籍证据门禁。

v0.48.0 已由九衡独立建立七政与四余十一曜身份目录，只保存传世名称、异名和四余五行名义。该目录没有运行或复制 `kinastro`/Horosa 代码，也没有采用其中的四余现代角色、Swiss Ephemeris 星位、宿界、宫制或限法；这些项目仍只用于列出后续需要验证的字段。

## 2026年9月27日奇门只读检查

`kinqimen` 的所读提交固定为 `e6680ac4ca0b0da5ce3fe637e05f9fc32066ec5a`，逐字节核对 README、配置和排盘三个文件，另读取完整 Git tree，19 个目录条目未截断。这是选定文件检查，不是完整源码归档身份门禁；原完整固定源清单仍为两个项目，没有把第三方运行伪报为已完成。

发现先前许可声明不足：README 宣称 MIT 并链接 LICENSE，但该固定版本的 LICENSE 返回 404，实际完整目录也没有许可证文件。登记状态已收紧为许可未闭合，禁止复制、分发和执行参考代码。本轮代码只在临时研究目录阅读，不进入源码包或运行依赖。

门、星、神与天盘的阴遁环序，中五与天禽分支，以及八位星环与本旬九星身份之间的差异，均已列为后续验证点，未认定任何一套是标准答案。《遁甲符应经》影印读取被网页工具文件大小限制阻断，本地下载连接超时，仍未取得实际字节或视觉核对原页。逐时排盘和正式规则门禁没有放行。

明细见 `data/research/kinqimen-source-inspection.json` 和 [本轮进度](CONTINUATION_2026_09_27_CLASSIFIER_QIMEN.md)。

## 固定源与对拍夹具

固定源清单位于 `data/research/reference-source-manifest.json`，保存 commit、tree、归档字节数与哈希、关键文件哈希、许可证状态和执行阻塞项。`scripts/verify-reference-sources.ps1` 可以对任意本地检出目录离线重算并核对整条身份链，不导入或执行第三方 Python。六组未来对拍输入位于 `data/research/reference-crosscheck-fixtures.json`，分别覆盖太乙年计/日计/時計与七政自校准案例/J2000/历史日界案例。所有用例的可信期望输出均为空，状态均为 `not_run`；机器测试会阻止它们被伪报为已执行或写入正式规则。

## 当前阻塞

两个优先仓库的源码身份已经闭合，但整包执行条件没有闭合：`kintaiyi` 缺完整依赖锁、网络/AI 隔离适配层、权威完整课例和九衡现代日期起局链；`kinastro` 另有许可证文件缺失、未固定 Git 依赖、AI/金融联网依赖、宿界与四余定义未决等问题。因此整包 `crosscheck_execution_allowed` 仍全部为 `false`，六组完整输入契约仍为 `not_run`。已完成的太乙静态表比较使用单独的范围与结果计数，不伪报为第三方整包已经运行。

正式规则种子仍为 0 条；本次登记不会改变任何术式参与状态，也不会产生结论、应期或行动建议。
