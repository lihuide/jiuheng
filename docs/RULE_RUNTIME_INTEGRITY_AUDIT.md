# 规则运行与融合完整性审计

## 目的

0.32.0 已能确定性执行单条已放行规则，但数据库中的 `engine_runs.signals_json` 仍是融合器的直接输入。如果只检查 Rule ID 是否仍获放行，而不从规则程序重新构造信号，损坏或伪造的保存信号就可能脱离规则输出进入融合。

0.33.0 封闭这条通道：任何术式信号都必须能从锁定问题、古代问题类型、术式排盘快照和完整 Rule ID 命中集合重新生成。保存字段只作为审计副本，不再作为无需验证的事实来源。

## 版本化运行输入

每次规则求值使用 `RULE_RUNTIME_INPUT_SCHEMA_VERSION = 1`：

```json
{
  "schema_version": 1,
  "method": "liuyao",
  "ancient_question_type": "project_outcome",
  "question": { "...": "锁定的完整 QuestionInput" },
  "chart": { "...": "该术式的确定性排盘或起法结果" }
}
```

运行输入拒绝未知顶层字段；`chart` 必须是 JSON 对象，最大 1 MiB。存储层从数据库重新读取锁定问题和古代问题类型，调用者只能提交已经计算好的术式排盘对象，不能替换问题文本、时间、地点或分类。

## 术内规则合并

算法版本为：

`jiuheng.rule_runtime.non_conflicting_signal_merge.v1`

同一术式可以有多条规则同时命中，但本版不按规则数量平均、不以优先级覆盖，也不把文献等级当作日常信号权重：

- 不同规则可以分别提供不同的标准信号字段；
- 多条规则提供同一字段时，值必须完全相同；
- 应期同样必须完全相同；
- 任一重叠字段值不同，整个术式结果失败关闭；
- 未命中、重复 Rule ID、未核验证据等级、越界信号、任意 `extra/option_scores` 或无效行动建议都不能进入结果；
- 术式证据等级取全部命中规则中的最弱等级，仅用于显示和既有僵局破局，不改变术式权重。

规则按 Rule ID 排序后合并，因此数据库返回顺序不影响结果。完成术内合并后，一个术式仍只向总融合贡献一个方法结果和固定 `1/N` 权重。

## 原子保存与不可变约束

`execute_and_store_rule_method` 对一个已锁定占问执行以下步骤：

1. 拒绝空白或不稳定的实现版本标识；
2. 拒绝向已有不可变综合裁决追加术式运行；
3. 拒绝同一占问、同一术式覆盖或重复运行；
4. 读取当前已放行且适用于该古代问题类型的全部规则；
5. 对同一个版本化输入逐条求值；
6. 无规则或无命中时保存“证据不足、不参与”的运行记录；
7. 有命中时先完成无冲突术内合并，再在同一事务写入 engine run 和所有 rule hits。

SQLite 迁移 v10 对新记录增加结构检查和跨表检查：术式必须与规则所属术式一致，可参与运行必须同时具有对象型排盘、信号、证据等级和完成时间；Rule Hit 必须具有对象型输入、`matched=true` 的输出和数组型轨迹。`engine_runs` 与 `rule_hits` 写入后禁止更新或删除。

## 融合前强制重放

融合器不直接信任保存信号。每个候选术式都必须重新完成：

1. 以锁定问题和保存排盘重新构造标准运行输入；
2. 重新执行该术式当前仍已放行的全部规则；
3. 核对保存 Rule ID 集合等于完整命中集合，不能只保留有利子集；
4. 核对每条保存输入等于标准输入；
5. 核对每条保存输出等于重新求值输出；
6. 核对每条保存轨迹等于重新求值轨迹；
7. 重新进行无冲突术内合并；
8. 核对保存信号和证据等级等于重新构造结果；
9. 通过后才交给同权融合器。

规则后来失去发布资格时，含该 Rule ID 的旧术式运行不参与新裁决。任何仍被考虑的运行只要存在输入、输出、轨迹、命中集合、信号或证据等级不一致，融合立即失败且不写入结论。

## 开发者模式与边界

历史详情的开发者模式现在可以展开术式实现版本、适用性、原因、排盘、标准信号、每条 Rule ID 的完整输入、输出和轨迹。

正式规则种子包仍为 0 条，所以这条运行链当前只在自动化测试夹具中完成端到端证明，不会让未考证规则进入产品。各术式的真实排盘适配器和正式古籍规则仍须分别通过既定证据门禁。
